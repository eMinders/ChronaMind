# Scope-Isolation Threat Model

**Task:** `MA-010` · **Status:** design document, nothing here is implemented yet except where a row
says *existing*. **Governs:** `MA-011` (selector semantics and the failing test), `E-011` (scope
hierarchy and path-based RLS), `E-014` (`ENTITY`), `E-017` (provenance rendering).
**References:** `ARCHITECTURE_V2.md` sections 5, 5.2 and 9.3; `V2-D25`; `V2-D27`.

The question this document answers: **by what paths could a caller learn that another tenant's
memory exists, what its attributes are, or how much of it there is, and what stops each path?**
The earlier architecture draft contained two critical defects of exactly this kind (a prefix match
and an unscoped entity table). This model exists so that a third cannot be introduced unnoticed.

## 1. Assets and adversary

| Item | Definition |
|---|---|
| **Asset** | Existence, content, attributes, counts and identifiers of memory belonging to a scope the caller cannot read |
| **Tenant** | A principal's personal scope, `/u/<id>/`, and everything beneath it |
| **Adversary** | An authenticated caller (or a compromised agent acting for one) that can issue any public-API request with any identifiers and selectors, observe every response, error and latency, and run many requests |
| **Not an adversary** | A holder of database superuser credentials, or code running inside the engine process (see section 5) |

"Observe" is deliberately broad: an error code, a row count, a field's presence or a response time
that differs depending on another tenant's data is a leak, even when no content is returned.

## 2. Observation paths

Every path is listed with its mitigation and the test that covers it. **Test status:** *existing* =
a test in the repository today; *planned* = named here so the owning task must create it; *accepted*
= no test, risk documented in section 4.

| T-09 | **Unauthorised cross-scope link**: `link_entity(a, b)` where the caller can read only one side | Existence of the other side; a bridge for later reads | Requires authorisation on **both** scopes; otherwise rejected with the same error as a missing entity | `…::test_link_entity_requires_both_scopes` | planned (`E-014`) |
| T-10 | **Provenance as a read oracle**: an abstraction derived from a source in an unreadable scope renders that source | Content or existence of the source | **Decided, `V2-D37`:** a reference into an unreadable scope renders as a per-caller opaque handle with no scope path, scope kind or source type (`scope.provenance.render_bundle`) | `tests/test_scope_provenance.py::test_unreadable_source_renders_without_scope_id_or_type`, `tests/test_scope_provenance.py::test_handle_is_stable_per_caller_and_uncorrelatable_across_callers` | existing (primitive) + planned (`E-017`, `E-035`) |
| T-11 | **Error-message discrimination**: "not found" vs "forbidden" vs "wrong tenant" | Existence of a foreign id | One error class and message for absent and unreadable; messages never echo identifiers or paths. v1 already raises static-code errors that do not echo input values | `tests/integration/test_retrieval_deletion_db.py::test_retrieval_requires_matching_tenant_context` (covers the v1 tenant-mismatch case only) | existing (v1) + planned (`MA-011`) |
| T-12 | **Aggregate leakage**: result counts, `coverage`, cost reports, deletion receipts, opportunity counts that include rows the caller cannot read | Volume of foreign data | Every aggregate is computed after scope filtering, over the read set only; receipts count only what the caller's deletion affected | `…::test_aggregates_ignore_unreadable_scopes` | planned (`E-017`, `E-037`) |
| T-13 | **Idempotency-key collision**: `idempotency_key` is globally unique, so a duplicate-key error reveals that another tenant used that key | Existence of a key (low entropy keys only) | Namespace the key by scope (the `I9` scope key) and make the conflict response identical to an in-scope duplicate. v1 returns `JobIdentityConflict` without the other row, but the conflict itself is observable | `…::test_idempotency_key_conflict_does_not_cross_tenants` | planned (`E-011`) |
| T-14 | **Pooled-connection context leak**: a stale `app.user_id` or `app.read_scope_prefixes` from the previous checkout | A previous caller's read set | Transaction-local settings only (`set_config(..., true)`); the guard rejects a transaction with a missing or mismatched context before any statement runs. v1 already requires a matching `app.user_id` | `tests/integration/test_clock_queue_db.py::test_clock_refuses_unscoped_idle_and_non_read_committed_transactions` (v1 context check); GUC reset test planned | existing (v1) + planned (`MA-011`) |
| T-15 | **RLS bypass by role**: a superuser or `BYPASSRLS` role ignores policies | Everything | A runtime role that is `NOSUPERUSER NOBYPASSRLS` with least-privilege grants, provisioned and catalog-verified by `security.provisioning` (#47, closed) | `tests/integration/test_rls_isolation.py::test_provisioned_role_is_restricted_and_every_user_table_forces_rls`, `tests/integration/test_rls_isolation.py::test_privilege_catalog_assertion_is_exact_and_detects_extra_or_missing_grants` | existing |
| T-16 | **Selector-count exhaustion**: more selectors than the 16-entry GUC limit | A bypass if the engine truncates silently | Exceeding the limit is a resource error, never a truncation; the error discloses nothing | `…::test_more_than_sixteen_selectors_is_an_error_not_a_truncation` | planned (`MA-011`) |
| T-17 | **Rank/score leakage**: approximate or post-filtered vector search ranks across tenants and filters afterwards, so the order or count of results depends on foreign rows | Relative similarity of foreign rows; result-count changes | The scope predicate is applied **before** ranking (v1 joins the temporal and tenant predicate into the ranking query and uses exact cosine). | T-18 | **Write-side oracle**: writing into a scope the caller cannot read | Whether that scope exists | Rejected before any row is constructed, with the same response for a nonexistent scope | `…::test_write_to_unreadable_scope_is_indistinguishable_from_missing` | planned (`E-011`) |
| T-19 | **Audit-log exposure**: `scope_read` events record the selector set, which contains scope paths | Paths read by others | Events are content-free, readable only by their owner, and never aggregated across tenants; the redaction guard is `RL-072` | `…::test_scope_read_events_are_not_visible_to_other_tenants` | planned (`RL-072`) |
| T-20 | **Backfill error**: migration `M2` writes `/u/<user_id>/` for existing rows with a wrong or colliding path | Cross-tenant rows after migration | Backfill generates paths from validated ids; a post-migration check asserts no row's path differs from its owner's and suite `I` reports zero exposure | `tests/integration/test_migration_m2.py` | planned (`E-011`) |
| T-21 | **Path normalisation**: `//`, `.`/`..` segments, surrounding whitespace, case or Unicode variants (NFC vs NFD) making two spellings address one tenant, or one spelling address two | Rows of another tenant via an alternative spelling | Canonical form only: `scope.paths.parse_scope` **rejects** empty segments, `.`/`..`, surrounding whitespace, control characters and a missing trailing separator rather than normalising them (normalising on input would turn a typo into an authorization decision). User-id segments stay broad for v1 compatibility, so Unicode and case variants of a user id are **distinct, byte-exact principals**; matching is byte-exact, so no variant reads another's rows. The residual is identity-layer impersonation (two look-alike ids), which is outside the engine (section 4) | `tests/test_scope_paths.py::test_malformed_paths_are_rejected_with_static_codes`, `tests/test_scope_paths.py::test_user_id_may_not_escape_with_relative_reference`, `tests/test_scope_paths.py::test_user_id_rejects_nul_and_whitespace` | existing |
| T-22 | **Deletion epochs**: the per-tenant deletion epoch (`MAX(deletion_epoch)` over `deletion_request`) and stale-epoch job rejections | Another tenant's deletion count or timing | v1: **no cross-tenant path found**; the epoch is read with an explicit `user_id` filter on an RLS-forced table, and a stale-epoch rejection is visible only to the owning tenant's worker and audit rows. | T-23 | **`audit_event.details` content**: the content-free `CHECK` (`audit_details_content_free`) forbids only the keys `content`, `evidence_span` and `embedding` | Memory content stored in an audit row under any other key, readable by whoever can read audit rows | Audit rows are tenant-scoped (forced RLS), so the exposure is within the tenant or to an administrator, not across tenants. The key blacklist is not a content guarantee: a redaction guard and a test of the `CHECK` are required | `…::test_audit_details_reject_content_under_any_key` | planned (`RL-072`); the `CHECK` itself is untested today (`INVARIANT_LEDGER.md`, Invariant 8 / content-free audit) |

Each finding below quotes the approved text it conflicts with. This document **raises** architecture changes;
it does not apply them (`APPROVAL.md`).

| # | Conflicting text | Finding | Status | Affected issues |
|---|---|---|---|---|
| 1 | `ARCHITECTURE_V2.md` section 5 (r2): "`path_with_prefix LIKE ANY(...)`" | `LIKE` is unsafe for prefix matching (T-02). **Measured on PostgreSQL 16.15:** `path LIKE '/u/4%'` returns `/u/4/` **and `/u/42/`**; with the trailing separator `LIKE '/u/4/%'` is correct for that case but `LIKE '/u/a_b/%'` also returns `/u/aXb/`; `starts_with(path, '/u/a_b/')` and `path ^@ '/u/a_b/'` return only `/u/a_b/`, and `starts_with` plans as an index range scan on a `text_pattern_ops` index | **Resolved by `V2-D35`** (r7): `LIKE` forbidden for scope matching | #54, #62 |

## 4. Accepted risks

Stated so they are decisions rather than omissions.

| Risk | Why accepted | Residual |
|---|---|---|
| **SQL-level timing differences**: index and plan choice vary with tenant density (the planner picks a sequential scan when one tenant holds most rows, per `REFACTORING.md` section 4) | Removing it needs constant-time execution the engine cannot provide | An adversary with many precise timing samples may infer the relative size of the table. Mitigated only by rate limiting at the API layer |
| **Shared-scope deletion affects other members** | This is authorisation by design, not a leak: a `project` row has several authorised readers | Project ACLs must be reviewed in the permission audit (`A-017`) |
| **Resource errors reveal the 16-selector limit** | The limit is public in the specification | None; the error carries no tenant data |
| **WAL, backups and replicas are outside the boundary** | Fixed by `D-ENG-04` | Isolation claims do not extend to copies of the database |

## 5. Out of scope

Superuser or host compromise; a malicious engine build; the LLM provider's logs; side channels
inside the model; and attacks that need an authenticated *insider with write access to the same
scope*. These are covered, where at all, by the deletion boundary (`D-ENG-04`) and by deployment.

## 6. How this document is kept honest

- Each *planned* test above becomes a requirement of its owning task; the task is not complete until
  the test exists and the row here is changed to *existing* in the same pull request.
- `INVARIANT_LEDGER.md` rows `I7` and `I17` are `PARTIAL` (r7 primitives, tested) and move to `ENFORCED`
  only when the engine-table tests for T-01 to T-10 exist.
- Adding an observation path means adding a row and a test. A path with neither a test nor an entry
  in section 4 is a defect in this document.
